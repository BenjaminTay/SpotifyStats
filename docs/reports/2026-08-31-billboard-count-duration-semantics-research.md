# 播放次数与全部收听时长双轨语义：调研、实施与验收

日期：2026-08-31；实施与验收更新：2026-09-01
状态：本地后端实施与真实副本验收完成；未 push、未部署
适用范围：播放分析、歌曲/专辑/艺人详情、首页、音乐查找、年度总结、Wrapped、Records 与 Billboard 单曲/专辑/艺人榜；不修改前端字段名或文案

## 1. 决策问题

本次要确认三个边界：

1. 30 秒（以及动态阈值）是否只决定一次播放能否贡献 `play_count`。
2. 单次播放不足 30 秒时，是否仍贡献这首歌的收听时长。
3. 同播放次数时，Billboard 的 `total_ms` 应表示全部有效收听时间，还是仅表示通过次数筛选、连续合并和余数筛选后留下的时间。

这不是官方 Billboard 计榜规则的复刻。项目的 Billboard 是个人历史榜单；`play_count` 和 `total_ms` 的排序、同分裁决以及连续播放合并都是 SpotifyStats 自己的产品规则。

## 2. 改动前实现核验

### 2.1 规则与调用链

改动前 [`playback-stats-rules.md`](../reference/playback-stats-rules.md) 的 R2/R3/R4.1/R32 共同表达了以下语义：

- 默认有效阈值为 `ms_played >= max(30000, duration_ms * 0.1)`；缺少曲长时回退到 30 秒。
- 默认先在完整时间线上按同曲、同来源和 session 间隔重建连续播放，再拆出完整逻辑播放和达到阈值的余数播放。
- 播放次数归到逻辑事件的 `counted_at`；收听时长按 `[ts - ms_played, ts)` 推断区间切片。
- 周榜按 `play_count DESC → total_ms DESC → 稳定实体键` 排序。

改动前默认 Billboard 数据链路在 [`data_loader.py`](../../backend/domains/billboard/data_loader.py) 中会：

1. 合并前将 SQL 最短时长设为 0，避免短片段在合并前消失。
2. 调用 `merge_consecutive_plays()` 重建逻辑事件。
3. 再调用 `filter_effective_plays()`。
4. 对保留下来的逻辑事件调用 `build_billboard_weighted_frame()`。

`build_billboard_weighted_frame()` 本身是双权重设计：事件行贡献次数，收听切片贡献时长。但它接收到的已经是阈值后的事件帧，所以改动前 `total_ms` 实际上是“合格逻辑事件的时长”，不是所有原始音乐收听区间的总时长。

### 2.2 当前行为的精确定义

在默认 `merge_enabled=true` 下：

| 场景 | 改动前 `play_count` | 改动前 `total_ms` |
|---|---:|---:|
| 孤立 20 秒播放 | 0 | 0 |
| 同一 session 的 20 秒 + 20 秒 | 1 | 40 秒 |
| 180 秒完整播放 + 同一 session 的 20 秒余数 | 1 | 180 秒 |
| 两个相隔超过合并间隔的 20 秒片段 | 0 | 0 |

也就是说，短片段不是完全不能进入时长：它可以先参与连续合并；但孤立短片段，或合并组中最终没有达到阈值的余数，会随逻辑事件过滤一起从 `total_ms` 中消失。

## 3. 外部口径能支持什么

Spotify 官方将歌曲 stream 定义为“至少播放 30 秒”，这能支持把 30 秒作为 `play_count`/stream 次数的资格线，但不能推出“不足 30 秒的实际收听时间必须从时长指标删除”。见 [Spotify：How your streams are counted](https://support.spotify.com/ca-en/artists/article/how-your-streams-are-counted/)。

Billboard 对公开榜单的描述是按 Luminate 追踪的 streaming activity（以及适用时的电台和销售）排名；公开说明没有规定个人收听总分钟数作为同分裁决键。见 [Billboard Hot 100 chart description](https://ca.billboard.com/charts/hot-100)。因此，`total_ms` 的具体含义需要由本项目产品决策冻结，不能声称是 Billboard 官方 tie-breaker。

## 4. 真实库与反例证据

### 4.1 决策阶段只读快照

数据范围：`data/spotify_stats.db`，核验日期 2026-08-31；只读查询和内存计算，未改写数据库。

- `music_only` 当前实现以 `track_id IS NOT NULL` 为准：92,568 条原始音乐候选记录。
- 低于 30 秒的原始记录：26,075 条，合计 98,866,014 ms，约 27.46 小时。
- 按动态阈值不合格的原始片段：26,092 条，合计 99,466,685 ms，约 27.63 小时。
- 当前合格逻辑事件轨：66,419 次，`total_ms=15,106,121,745`。
- 单独保留完整推断收听区间的时长轨：`total_ms=15,207,305,781`，比当前多 101,184,036 ms，约 28.11 小时。

其中一部分短片段会在连续合并后形成合格逻辑播放，因此原始短片段总时长不能直接当成最终增量。按同一周、同一 `track_id` 对账，在当前已有合格播放的 37,773 个歌曲-周组合中，10,672 个组合存在当前口径未计入的额外收听时间，合计 53,099,554 ms；其中 10,215 个处于同播放次数竞争组，涉及 217 个周，合计 47,409,258 ms。

这些数字是当前数据库的证据快照，不代表将来导入后的固定值；它们用于证明该语义会影响实际同分排序，而不是证明某个具体歌曲的最终名次。

### 4.2 最小反例

假设歌曲时长 180 秒：

- 只听 20 秒：不应贡献一次合格播放，但如果产品要统计真实收听时间，应贡献 20 秒。
- 同一 session 听了 20 秒，再无缝听了 20 秒：合并后贡献 1 次和 40 秒；这已经是当前实现。
- 同一 session 听满 180 秒后又听了 20 秒：应贡献 1 次；当前 `total_ms=180 秒`，全时长方案为 200 秒。

第三个例子直接区分了两种 tie-breaker：如果另一首歌也是 1 次、180 秒，那么全时长方案会把多听 20 秒的歌曲排在前面，当前方案会进入后续稳定键裁决。

### 4.2 实施验收时的当前真实库

## 5. 已冻结并实施的目标语义

### 决策 A：阈值只约束次数

30 秒和动态阈值只回答“这段收听是否产生一个有效播放事件”。它不删除已经发生的、可由导出数据支持的收听时间。

### 决策 B：时长使用全部有效收听区间

`total_ms` 定义为：

```text
weekly_total_ms(entity, week) =
    sum(有效音乐收听区间与该 Billboard 周的交集毫秒数)
```

其中：

- 仍先进行全局连续时间线重建，避免同一时间重叠和合并边界造成重复计算。
- 单次不足 30 秒的音乐片段，只要时间和曲目身份有效，就计入时长。
- 不计入非音乐记录、无效/负时长、无法可靠归属的时间，以及重叠去重后不存在的时间。
- 跨 Billboard 周的收听区间按实际区间切片；播放次数仍按逻辑事件 `counted_at` 归属。两条轨道不互相改写。

### 决策 C：同次数按“全部有效收听时长”裁决

周榜排序冻结为：

```text
play_count DESC
→ weekly_total_ms DESC
→ stable entity identity ASC
→ normalized display text ASC
```

这里的 `weekly_total_ms` 不是展示层四舍五入后的小时数，也不是只保留合格逻辑事件后的 `ms_played`；它是同一周、同一实体归属范围内的精确收听区间总和。

这个选择的产品解释是：第一排序键衡量“达到 Spotify 式播放资格的次数”，第二排序键衡量“同样次数下实际投入了多少收听时间”。由于次数优先，短暂跳过行为不会单独让一首歌进入周榜；它只有在两首歌有效播放次数相同的时候才影响顺序。

## 6. 未采纳或需要明确拒绝的方案

### 方案 1：先删除所有不足 30 秒原始行，再合并

不建议。它会把两个本可组成完整播放的连续片段拆散，改变播放次数，也会丢失真实收听时长；与当前“合并后判定”的设计和已有回归测试冲突。

### 方案 2：次数和时长都只使用合格逻辑事件

这是改动前实现，现已停止作为最终语义。它简单、排序可复现，但会让“听了 20 秒”在统计时长上等于“完全没听”，也会使合并组的未达阈值余数静默消失。

### 方案 3：将短片段计入全局听歌时长，但 tie-breaker 仍使用合格事件时长

不建议。这样会产生两个都叫 `total_ms` 的不同事实：详情/分析页显示一套时长，Billboard 同分排序使用另一套时长，解释“为什么这首歌赢”时无法对账。

## 7. 后端实施

提交 `911256f1`（`feat: 统一全部收听时长统计口径`）完成以下修改：

1. 在逻辑时间线中增加显式的全部音乐收听时长帧；次数事件和时长区间不再共用阈值后的同一帧。
2. 播放分析、实体详情、首页、搜索快照、年度总结、Wrapped、Records 与 Billboard 全部复用该时长轨；原 API 字段名保持 `total_hours`、`hours`、`total_ms` 等现状。
3. Billboard 预聚合升级为 `billboard_aggregation_v4_all_duration`，搜索统计升级为 `music_search_snapshot_v10_all_duration` / `music_search_chart_v10_all_duration`，使旧派生数据自动失效。
4. Billboard 排名在排序前强制保留 `play_count > 0` 的候选，因此 0 次但有时长的实体只能出现在普通统计和搜索上下文，不能靠时长进入榜单。
5. 原始 `plays`、曲目、专辑与艺人元数据均不重写；前端代码、字段名和显示文案均未修改。
