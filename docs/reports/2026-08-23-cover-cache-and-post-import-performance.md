# 封面缓存与导入后性能修复报告

状态：Pass。代码、真实库封面补下载、性能探针与本地完整门禁均通过；未执行生产部署。

## 问题与根因

- 新导入专辑的 Spotify 图片已经存在于 `spotify_album_meta`，但没有同步到 `albums.image_url`。多数消费接口只在本地实体已有 URL/path 时才输出 `/covers`，因此 186 张已知来源的专辑既不显示，也不会触发下载。
- 导入维护只刷新曲目和专辑，不批量维护新艺人的 Spotify ID、元数据与图片。懒加载下载只覆盖用户实际打开过的实体。
- `cover_download` 处理器吞掉 HTTP/文件异常，队列随后仍把任务记为 `done`；任务去重只使用数字 ID，专辑 42 与艺人 42 还可能互相阻挡。
- 覆盖式导入清空预聚合并全量重建，真实库这段约 3.3 秒；更大的延迟来自六套搜索精确快照重复加载终身播放帧、构造未消费的完整 Billboard slices，以及每个变体清空首页依赖的小快照。
- 首页使用全局 Billboard snapshot revision。其他口径的搜索变体写入时，即使默认首页快照未变，也会造成首页缓存 miss。

## 已实现

- 曲目批量 API 同步精确本地艺人 ID，再批量获取艺人详情；仍缺失时只接受规范化名称完全相同的 Spotify 搜索结果。
- 专辑/艺人有效图片源同步到本地实体，导入后自动扫描播放相关实体并排队下载。
- 下载任务按 `job_type + entity_type + entity_id` 去重，最多三次任务级尝试；HTTP client 内另有短暂网络/限流重试。图片经过状态、大小与签名校验后原子发布，数据库路径最后更新。
- 首页和最新完整榜单在搜索快照排队前预热；年度总结预热由搜索快照完成后触发。
- 音乐查找 metric map 改为 Pandas 向量聚合；chart context 只构建 summaries 和 power scores。变体间保留 latest snapshot，首页 revision 改为精确 key 级版本。

## 真实证据

- 数据库：92,908 条播放，SQLite `PRAGMA quick_check=ok`。
- 封面补下载任务：新增第一阶段 401 个、精确艺人兜底 147 个；最终历史 `cover_download` 共 1,135 个 `done`，本轮没有 `failed`，实际文件均大于 1 KiB。
- 播放相关专辑：2,930 个有 URL、路径和实际文件，缺失 0。
- 播放相关有效署名艺人：1,235 个中 1,185 个有 URL 与实际文件；剩余 50 个没有精确 Spotify 同名或可验证图片源，未使用模糊首条结果补齐。
- 数据库副本默认搜索快照 context：优化前 42.279 秒，最终优化后 11.916 秒，实体数同为 7,956。
- 数据库副本基线：周榜冷 2.803 秒、热 0.001 秒；首页冷 4.909 秒、热 0.011 秒；全量 Billboard 预聚合 3.284 秒。
- 开发 HTTP 服务稳定热态：首页 0.140/0.130 秒，周榜 0.169 秒；启动或热重载期间仍有一次后台预热成本。
- 本次交付验证：后端 unit 1,102 项、contract 358 项、前端 548 项、前端生产构建、本次变更 Python 文件 Ruff、文档审计和 `git diff --check` 通过。

## 仍有边界

- 当前串流导入仍是覆盖式重建，不能在没有源记录增删指纹的情况下安全断言为 append-only；周预聚合仍全量构建。旧周增量复用需要同时证明删除/修订、连续播放跨周边界、artist identity/track credit revision 与 album project membership 均未改变。
- 50 个艺人署名没有可验证 Spotify 图片。它们可能是本地化别名、影视角色/组合署名、从歌名解析的 featured 文本或 Spotify 无图实体；保留占位比错误关联更可靠。
