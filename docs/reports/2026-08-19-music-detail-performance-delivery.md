# 音乐详情性能优化与旧子页收口交付报告

> 状态：Pass
> 证据日期：2026-08-19
> 范围：本地代码、真实本地数据库探针、自动化测试与本地浏览器验收；不代表生产环境已经发布或复验。

## 结论

歌曲、专辑、艺人详情已从“进入页面即下载完整榜单与成员数据”改为“实体摘要和播放统计并行、其他子视图按需加载”。优化没有改变播放统计、榜单详情或成员排行事实：优化前保存的 8 组 JSON 与优化后结果逐对象完全一致。

本轮同时从前端消费入口移除歌曲歌词、专辑发行档案、艺人发行周期和艺人生涯。后端既有只读能力与相关组件源码暂时保留，便于后续重新设计；旧 `tab` 深链会规范化回播放统计，不会在后台继续请求已移除页面的数据。

## 实现边界

- 详情接口保留 `view=full` 兼容响应，新增按 revision 缓存的 `summary`、`overview`、`tracks`、`albums`、`project` 无损视图。
- 首屏的摘要与实体播放统计使用独立 TanStack Query 并行请求；同一统计 query key 由 Query 层去重。
- 专辑和艺人的榜单概览、成员歌曲、成员专辑只在打开对应页签后请求。
- 艺人成员歌曲由服务端分页；Desktop 每页 50 条、Phone 每页 20 条。周榜长历史每次只挂载 50 行，避免一次创建全部 DOM。
- 只需要播放次数和次数排行的路径不再构建时长切片；同一请求内复用排行作用域。播放次数与收听时长的既有计算规则均未修改。

## 优化前后等价性

在修改前从真实本地数据库保存代表性歌曲、专辑、艺人的完整详情、播放统计，以及专辑和艺人成员排行响应。修改后用相同过滤参数重新请求并比较规范化 JSON，共 8 组全部相等：

| 对比对象 | 结果 |
|---|---:|
| 歌曲 / 专辑 / 艺人完整详情 | 3 / 3 相等 |
| 歌曲 / 专辑 / 艺人播放统计 | 3 / 3 相等 |
| 专辑单曲排行 / 艺人单曲排行 | 2 / 2 相等 |
| 合计 | 8 / 8 相等 |

可重复使用 [`../../scripts/music_detail_equivalence_probe.py`](../../scripts/music_detail_equivalence_probe.py) 校验完整响应与各子视图的无损关系，并通过 `--baseline-dir` 与预先保存的详情基线比较。基线目录和真实数据库只作为本地验证工件，不进入 Git。

以下是同一次本地热缓存探针的响应体大小和耗时快照。单次耗时受机器与缓存状态影响，只用于说明本次验证环境，不作为生产 SLA；响应体缩减是接口结构本身的确定性结果。

| 实体 | 优化前完整响应 | 优化后首屏摘要 | 响应体缩减 | 摘要耗时 |
|---|---:|---:|---:|---:|
