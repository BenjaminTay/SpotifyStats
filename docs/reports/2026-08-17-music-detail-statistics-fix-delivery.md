# 歌曲、专辑、艺人详情统计修复交付报告

日期：2026-08-17

## 结论

歌曲、专辑、艺人详情页的总播放时长、播放时长排行、艺人最近 50 次和版本拆分统计已完成修复。详情页现在与逻辑播放时间线 V2 使用同一套次数/时长双轨规则，未修改原始 `plays` 数据，也未执行 SQLite 数据重建。

## 问题与根因

### 1. 详情页时长继承全库切片

`filter_period()` 会把全库时长切片放入 `DataFrame.attrs`。Pandas 在实体过滤时保留这些 attrs，歌曲、专辑和艺人详情随后使用了全库切片，导致实体播放次数是局部值，但总时长、活跃天数和分布时长是全库值。

### 2. 时长排行污染

详情页播放排行的 `hours` 聚合也从继承的全库切片构造，因此艺人或专辑的时长排行会混入其他艺人、其他专辑，甚至出现播放次数为 0 但时长非 0 的行。

### 3. 艺人最近 50 次按 fan-out 行计数

艺人统计会将合作曲按署名 fan-out 展开为多行。旧逻辑直接取最新 50 行，导致“最近 50 次”不是 50 个逻辑播放事件。

### 4. 版本拆分使用原始静态计数

歌曲版本组和专辑发行组曾直接对原始 `plays` 使用 `ms_played >= 30000` 计数，没有经过连续播放合并、动态阈值和逻辑事件生成，因此与详情/榜单主统计口径可能不一致。

### 5. 相对窗口使用服务器当前日期

`last_4_weeks` 与 `last_6_months` 以服务器当天为结束日。当前数据源停止在更早日期时，详情页的相对窗口会落入空白数据区间。

## 修复内容

- 新增实体范围的 `build_duration_frame()`，从显式传入的实体逻辑事件重新生成时长切片，不读取隐式全库 attrs。
- 详情摘要、小时/日期/星期/月/年分布和详情排行统一接收实体时长帧；播放次数继续来自逻辑事件行，时长继续来自切片行。
- 艺人最近 50 次先按 `_logical_event_id` 取最近 50 个事件，再按目标艺人计数，并对 fan-out 结果再次按事件去重。
- 版本组和发行组接入 Billboard 的 weighted frame，使用独立 `play_count` / `total_ms` 覆盖版本明细统计。
- `last_4_weeks` / `last_6_months` 改为以当前有效播放帧的最新 `ts_date` 为结束日。
- 增加实体时长隔离、相对窗口锚定和版本加权统计回归测试。
