## 实现与语义

- 发行周期通过既有 project resolver 识别目标；专辑播放取与个人对比一致的 L2/L3 song membership 和逻辑事件，不先按主署名或来源专辑名丢弃合作曲。
- 主发行优先采用已有高置信 project Spotify 绑定；明确成员版本保留自己的日期锚点。同项目不同版本允许共用播放成员，普通个人对比仍拒绝重复实体。
- 无明确项目绑定时，高置信播放容器关联仍须确认目标版本及艺人；不得用同名其他 ID 或更早日期代替。组合署名原声带使用既有稳定 Album 到 project 绑定及完整来源艺人 ID，不把项目播放 fan-out 给表演者。
- 只消费合法 confirmed/day；粗日期、来源缺失、身份缺证、冲突、对象不存在和版本歧义分别返回原因。空播放窗口不再清空已经可证明的排名和全历史半数播放距。
- compare 全链应用只读 guard 和源 revision fence。打开表格不补证、联网、写库、排队或冷建榜单；缺失/损坏快照继续拒绝读取。
- 前端保留对比列、部分成功、等待、逐项不可用与请求错误，提供读取重试。上游普通榜单失败时，发行周期区域仍然挂载；真实零与不可计算不混淆。
- 维护按语义缺证选源；同一官方响应安装日期和有序 Album artists，纯证据维护不抓曲目分页。确认到年/月及待审核冲突不反复抓取。项目日期同步复用相同主来源合同，保护人工日期和关系。
- 显式 `--include-compilation-variants` 可准备/验证/转移八个榜单上下文；manifest 声明并严格验证范围，旧四上下文格式保持兼容。

## 原始诊断与来源维护

初始本地有 96,881 条播放、3,394 条 Spotify Album 缓存，其中 3,132 条缺日期 precision。默认 L2 选择器 520 项仅 25 项通过旧发行资格；L3 496 项仅 20 项通过；四个含精选集上下文返回 503。既有缺失 Album 选择器返回 0，不能修复此类证据缺口。

受控清单有 3,380 个引用来源，3,125 个需要补证，分 16 批、每批最多 200 ID；14 个孤立缓存单列，没有自动抓取。全部 3,125 个来源已取得官方响应。初轮有三组各 20 个请求失败，仅重试缺失部分后全部完成。来源响应只保存 id、名称、类型、日期、precision 与 artists，留在私有 ignored 目录。

副本日期安装结果为 3,124 accepted、1 conflict，Album artists 为 3,125 observed。跨年份冲突的旧值保留，不自动覆盖。后续恢复判据按每个实际项目的来源和日期合同计算，不能把 HTTP 成功数当作可计算专辑数。

原始及治理事实 30 类在初次安装副本逐行摘要一致，包括 plays/tracks/track_artists、人工覆盖、稳定身份、L1 关系、project membership、已批准 project external 绑定及 Album 容器关联。最终准备源的保护核对随实际应用阶段另行登记。

## 隔离准备与接口结果

最终代码在新的 Online Backup 副本 `prepared.db` 重放固定响应，保留早期候选及其记录。搜索四统计变体通过 `--statistics-reuse-only --require-all-ready`，原精确事实复用，没有冷建。八个 Billboard 上下文的 96 个发布项已 ready，涵盖 L2/L3、动态阈值及精选集，2022–2026 年份；四套详情投影 ready，共 283,472 条来源事实。

剩余无目标发行日包括仅关联其他发行版本的情况，例如 Flicker 的已知容器为 Deluxe；不同地区来源的已确认日期相差一天以及其他多来源冲突保持审核，不能为了消除空值取最小/最大日期。原声带来源中不具备项目绑定或有效身份的情况同样单列。完整逐项清单在下述私有证据中，正式验收仍需检查这些分类和页面表达。
