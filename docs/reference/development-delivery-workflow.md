# 开发、整合与工作树收尾规则

适用读者：维护者与Agent。本文是共用技术参考；日常操作见[使用指南](../user-guide.md)，实施与验收证据见[报告索引](../reports/README.md)。

本规则约束任务负责人、共享文档、提交和工作树的生命周期。业务正确性、本地验收、CI、发布与生产验收仍按各自合同判断，分支整理不能替代产品验收。

## 任务与负责人

- 开发前在[开发状态总表](../DEVELOPMENT_STATUS.md)确认事项稳定 ID、唯一研发负责人、当前基线、修改范围和下一步。同一问题链只保留一个活跃研发分支；关联问题可以共用负责人。
- 并行工作必须有明确独立范围。多个任务涉及同一统计、缓存或启动路径时，先由协调负责人划分实现范围；其他任务可提供诊断或审查，不各自修改同一条链路。
- 开发状态总表、问题台账、文档地图、变更日志及跨任务共享规划由协调负责人统一合并。研发负责人维护业务补丁与专项证据，通过交接说明提供状态增量，不在每个候选工作树复制一套共享文档。
- 开始新阶段前检查已有分支和工作树。通常复用当前研发工作树；需要同时比较原版与候选时，优先使用固定提交与独立运行副本。确需保留并行源码候选时，记录原因和退出条件，旧候选先冻结归档。

## 检查点与状态

| 状态 | 含义 | 必须明确的下一步 |
| --- | --- | --- |
| ACTIVE | 当前负责人正在开发或有界定位 | 目标、范围与本轮结束条件 |
| READY | 补丁固定，可交独立审阅或整合 | 基线、精确文件、验证及剩余边界 |
| INTEGRATED | 改动已进入 main | 源提交到主线提交映射、交付或清理 |
| HOLD | 有明确依赖或暂缓原因 | 恢复条件；长期暂缓转归档 |
| ARCHIVED | 实验停止、方案未采用或已被替代 | 可恢复位置与处置理由，不表示正在开发 |
| CLOSED | 约定开发与交付范围结束 | 已完成分支和工作树清理，证据独立保存 |

- 当前状态、优先级、下一步和最后核验日期只维护在总表；问题台账保存身份、复现与判断依据，报告保存阶段过程。实现、验证、提交、推送和部署分别记录。仅实现或专项通过不得报告整项“完成”。
- 一个可审核阶段通过相应检查后，应形成精确检查点，无需等待生产验收才保存成果。用户已授权提交时，检查 staged diff、必要文档、相关检查和 hooks 后提交；未获提交授权或实验未采用时，保存基线 SHA、补丁、未跟踪文件和处置说明。
- 提交只包含当前任务的明确路径或 hunks，禁止把其他任务改动、运行数据或整个 dirty worktree 一并暂存。
- 检查点不得把未通过的资源准入、局部门禁或旧版本证据描述成当前完整通过。性能候选没有证明收益时，可以明确归档，不为保留分支继续扩展实验。

## 整合与提交映射

- 整合前比较实际内容，区分原提交已合入、重写提交已吸收、后续实现已取代，以及真正遗漏的改动；“独有提交数”不直接等于待合入修复数。
- 同一问题优先沿明确的提交链整合，避免反复复制未提交文件。跨任务联合整合或重写提交时，在交付报告记录源分支/源 SHA、主线对应 SHA、冲突取舍与验证范围。
- 主线已有修复时不重复合入旧实现。对混合历史补丁逐项判定：已覆盖部分关闭；仍有价值部分按当前 main 提取最小候选；未采用部分归档。不得整体合并过时的资源或统计实现。
- 全局状态文档以 main 为准。整合后的研发/整合工作树应安全同步 main，先保存未提交改动，只处理明确重叠路径，不用整树 reset/clean 解决文档冲突。

## 证据与清理

- 同日同题的阶段实施、审阅和验收优先维护一份主题文档，以章节区分阶段；新进展追加到既有文档。不同主题、独立交付边界或过长且可独立阅读的内容再拆分，不为每次检查单独新增报告。
- 合并时先给主题结论和阅读顺序，保留各阶段的源码版本、数据范围、失败与未完成边界；删去重复背景和已被正文承接的后续清单。更新索引与章节深链后移除原文件，不在仓库另存全文副本或空壳跳转。
- 验收报告入 Git，原始日志、浏览器材料、数据库副本与运行产物保留在独立本地归档。报告记录归档 ID、目录及恢复方式，不让长期证据依赖一个已结束的工作树。
- 迁移证据前核对运行中进程和当前消费者；先保存补丁与未跟踪文件，再迁移输入和更新使用方路径。历史收据保留原样，用 old→archive 映射解释路径变化，禁止覆盖原失败或篡改原计时。
- 移除 dirty 工作树前必须验证已保存的补丁、变更文件和证据可恢复；环境/正式数据符号链接不跟随，当前运行副本和正式数据不纳入清理。
- 交付结束后在同一次收尾处理源分支与工作树。临时需要保留时记录消费者和移除条件，不以“以后可能有用”为由无限保留。
- 常态保留 main、每条活跃问题链一个研发工作树，以及至多一个统一整合工作树。恢复引用和归档目录不计为活跃开发分支。
- 本地清理与远端清理分开执行；远端分支删除、推送和发布分别遵循用户授权。共享分支删除前确认消费者，源提交已有恢复点不等于可以擅自改远端。

## 交接内容

交接保持简短，至少给出事项 ID、负责人、基线/当前提交或补丁位置、精确范围、验证结果、未完成边界和下一步。采用重写整合时补充提交映射；结束时补充证据位置及分支/工作树处置。详细数据放专项报告，不重复复制到每个共享入口。

## 文档读者与命名

项目首页面向使用者，说明产品、界面与开始使用；使用指南承担操作和常见问题；开发、设计与运维文档按维护目的保留必要技术细节。Agent文件只承担执行指令与选读入口，共用规则链接到唯一技术参考。

长期台账、当前规则、滚动路线使用稳定主题文件名；日期放正文。冻结设计、验收／发布报告及归档保留日期，协议版本只有在区分合同含义时保留。改名与内容迁移应更新文档地图、相对链接和章节锚点，检查是否遗漏独有规则或证据。
