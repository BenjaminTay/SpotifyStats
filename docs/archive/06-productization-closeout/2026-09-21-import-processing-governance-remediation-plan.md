## 1. 目标与依据

把一次导入变成可解释、可恢复、按影响范围处理的完整更新：原始输入、活动播放事实和指纹基线能够对应；关键统计不被封面任务拖延；失败能在正确边界恢复；历史治理欠账不再与本次导入失败混为一谈。

本规划复用现有增量算法、SQLite staging、Online Backup、ChangeSet、持久任务队列和快照发布机制，不另建通用 ETL 平台。

依据按证据类型区分：

- [数据导入与健康规则](../../reference/data-import-and-health.md)、[音乐源数据管理规则](../../reference/music-metadata-management.md)：当前安全、统计与治理合同。

## 3. 范围与实施原则

### 3.1 本规划覆盖

- 串流输入的暂存、预检、计划确认、写入、发布与成套恢复。
- 基线状态、导入批次、阶段进度、后台依赖和失败报告。
- 与本次数据变化有关的身份、归并、Album Project、L3、Billboard、搜索及既有下游快照维护。
- 零播放兼容身份和无曲目音频的可解释治理。
- Settings 既有入口的状态、报告、恢复操作及桌面/移动验收。

### 3.2 非目标与边界

- 不更改播放次数/时长双轨、连续同曲合并、L2/L3、完整榜单周等统计语义。
- 不恢复旧消费页面，不引入 LLM 判定身份、近似重复或未知语言/流派。
- 不重写增量引擎，不新增消息中间件、分布式调度、数据湖或独立管理应用。
- 不将 `data/account` 与没有账号数据的新串流包一起覆盖。账号导入共用安全协调边界，但不在本轮重新设计其业务 ETL。
- 不自动删除原始 JSON、播放事实、旧备份或历史别名；人工治理遵循覆盖层、revision 与审计规则。
- 规划阶段只新增本文和文档地图；后续实现先在隔离副本验证。正式数据写入、提交和部署各自按届时明确任务范围执行。

### 3.3 先定义可用性，再划分恢复边界

分别表示：源文件与事实是否一致、当前统计是否可用、质量问题是否需要治理。普通元数据缺口不阻断已经证明正确的播放事实；实际影响当前播放统计的身份冲突、无效人工覆盖和 L3 硬问题仍然阻断相应统计发布。

发布后禁止因为封面或可重建快照失败，自动用旧整库快照覆盖已经被新操作使用的数据。恢复失败或 generation 漂移时必须保留明确的 `recovery_blocked`，不能继续静默写入。

## 4. 目标合同

以下状态和字段是待实现的设计约定，实施时在现有模型上增量扩展，不宣称当前 API 已支持。

### 4.1 输入包与活动原始数据

输入包经受认证的本地管理入口导入应用控制的暂存目录，生成不可变清单；预检、执行及重试读取同一份输入。浏览器侧使用文件上传/目录文件集，不把客户端路径当成服务器目录；本机脚本可以显式导入本地目录，但必须走同一服务。GET 仍只读，不负责接收文件或创建导入批次。

在现有导入路由下扩展创建批次、按批次预检、执行、查询和重试能力；具体 URL 在 S1 根据现有 schema 固化。执行入口以 `batch_id` 和绑定批次/基线的确认标识为准，不接受任意读取主机路径的公共接口。默认直接读取 `data/streaming` 的旧入口保留兼容适配，但不得绕过批次协调。

| 输入关系 | 播放事实动作 | 成功后的活动原始数据 |
| --- | --- | --- |
| 相同指纹集合 | noop | 保留当前批次；重分包可登记为等价输入，不重写事实或重建派生 |
| 完整快照超集 | 追加新增指纹 | 新完整包作为活动原始快照 |
| 可证明的尾部增量包 | 追加新增指纹 | 上一活动完整来源加本次增量来源；不能用尾包替换全部历史 |
| 确认后的历史快照修订 | 精确 reconcile | 以确认后的完整快照为活动来源，旧原始文件留作历史 |
| 旧库无基线，确认完整输入 | full 初始化 | 新完整包与新基线绑定 |
| 不完整、异账号或证据不足 | 阻断自动执行或要求明确替换计划 | 保持现有活动来源 |

尾部增量的累计来源通过版本清单引用不可变原始文件，允许来源间精确重复并统一去重；同名文件不能相互覆盖。完整性按有效源记录集合验证，不要求不同导出分包有相同文件名。历史被替换或 reconcile 移除的原始记录仍可保存在归档中，但不得继续进入活动来源集合。

`data/streaming` 保留兼容使用方式；新增活动来源 resolver 后，所有导入、预检与重放入口须读取同一版本清单。迁移前先登记现有目录，不猜测其与数据库已经一致。已有目录被用户提前覆盖时，必须显示“旧原始恢复点不可证明”，不能承诺成套回滚；有经验证的旧备份才允许接管恢复点。

### 4.2 最小持久记录

优先扩展现有 `playback_import_runs`、活动状态和后台 job，必要时增加有明确外键的批次/阶段记录：

| 数据 | 必需内容 |
| --- | --- |
| 输入批次 | batch/run ID、输入种类、manifest/digest、指纹合同版本、来源批次链、创建时间 |
| 执行计划 | requested mode、relation、可比较性、旧/新 count/digest、增删复用、确认标识 |
| 活动发布 | 旧/新 generation、活动原始版本、数据库恢复点、发布进度 |
| 阶段执行 | stage、attempt、依赖 target、状态、排队/运行时间、处理范围、策略及 fallback reason |
| 恢复与错误 | 稳定错误码、关联 job、恢复结果、是否可重试、被取代原因 |

账号身份继续使用现有命名空间 hash；不把用户名、IP、原始记录或密钥写入普通日志和可提交报告。避免把全部指纹复制到多套运行表，复用当前基线与 staging。

原始文件和数据库之间无法用单个 SQLite 事务完成原子提交。需要一个小型、持久化且不随整库恢复消失的发布日志，记录候选批次、恢复点和进度；日志不得成为第二套统计事实源，恢复前仍核对数据库与源清单。失败尝试的诊断也必须在恢复旧库后可查。

### 4.3 发布与恢复状态

```text
输入暂存 → 预检/确认 → prepared → facts_committed → sources_published
                                                    ↓
                               核心维护/校验 → core_ready
                                                    ↓
                                 精确快照维护 → ready
```

- `prepared`：输入冻结，恢复点可读，已取得写入协调权，尚未变更活动事实。
- `facts_committed`：事实、基线、ChangeSet 与发布意图同事务提交；原始来源指针可能尚未切换。
- `sources_published`：活动源版本与事实 generation 已匹配。此后源/事实发布结束，统计按各自状态开放。
- `core_ready`：当前播放身份和必需统计满足合同，候选索引及关键页面可用；其他快照可继续 warming。
- `ready`：本批次必需派生集合全部就绪；封面完成度和质量警告独立记录。

任务状态 `pending/running/retryable_failed/blocked/succeeded/superseded` 与数据新鲜度 `ready/warming/unavailable/failed` 分开存储和映射。只有确有有效更新任务且正在服务旧事实时使用 warming；首次无快照、无任务或失败不能一律显示 warming。

兼容当前 `maintenance_pending/success/noop/recovery_blocked` 的迁移映射必须写入测试；旧 `success` 不应被追溯解释成所有后台快照和封面已完成。

| 故障位置 | 必须达到的行为 |
| --- | --- |
| 暂存、确认、备份失败 | 保持原始活动文件和数据库不变 |
| 事实事务提交前 | rollback，保留失败证据 |
| 事实提交后、来源切换前 | 阻止新写入与混合批次读取；重启核对日志，完成切换，或在无后续写入时成套恢复 |
| 来源切换后、核心维护未完成 | 保留已发布批次；重试安全阶段，相应统计使用合法 LKG 或明确 unavailable/failed |
| 精确快照、外部元数据或封面失败 | 不回滚播放事实，按阶段/实体重试，保留真实状态 |
| 证据损坏、目标 generation 已过期 | 拒绝覆盖当前代际，标记 blocked/superseded 并说明原因 |
| 整体恢复自身失败 | 停止后续写入，暴露恢复状态和本地恢复点，保留全部证据 |

S1 必须协调 API、后台任务、账号导入及本机维护脚本这些实际写入者。发布临界区使用同一写入协调协议；不得仅依赖当前进程的导入锁。恢复整库前停止相关 writer、关闭/刷新连接与缓存并确认没有后续提交。不得在已开放其他写入后自动覆盖旧快照。发布窗口读取只能返回受版本保护的 LKG 或明确暂不可用。

### 4.4 三种治理范围

| 范围 | 用途 | 对导入的影响 |
| --- | --- | --- |
| changed closure | 本次变化曲目及其 owner、L2/L3、Album Project、艺人和周/年依赖 | 优先定向处理；无法证明完整影响范围时安全回退 |
| played works | 全部有播放事实的工作 | 保障实际统计归属；硬冲突不能降级为普通提示 |
| all identities | 所有历史身份和兼容别名 | 完整治理与债务跟踪，不因零播放历史问题直接回滚本次导入 |

阶段报告必须给出范围、分母、问题数量和受影响播放/时长。`played works` 问题为 0 不意味着 `all identities` 治理完成；单个阶段使用 changed closure 也不意味着全局健康为 0。

### 6.1 性能门槛

- 预检沿用 21 个 hot 原始样本和 P95 ≤500 ms；缺基线与 ready 基线分别测量。不能把此前缺基线的约 59.7 ms P95 当作 ready 基线成绩。
- 冷预检记录至少 3 个独立进程样本与 median，保留完整 payload 等价；本规划不在未测 ready 基线前承诺冷耗时数字。
- 真实导入对照至少 3 次可比副本运行，分别记录核心可用耗时、全部必需快照就绪耗时、各阶段运行/排队耗时和峰值资源。
- 性能对照冻结数据、设置和外部响应，恢复相同 seed；不能因缓存冷热、Spotify 网络波动或不同语义产物得出加速结论。
- S0 测量后、S3 修改前在阶段报告固定时间目标与容忍范围。无可测改善时只交付已证明的调度/重复计算消除，不宣布整体提速。
- 确定性门槛：1,204 个待执行封面不能成为关键 job 的前置排空条件；依赖满足后应由保留的执行能力调度。不得靠放宽请求超时或取消统计校验通过。

## 8. 风险、决策与最终完成定义

| 风险 / 未知项 | 处理决策 |
| --- | --- |
| 原始目录与 SQLite 无共同事务 | 使用持久发布日志、写入协调、读取版本保护和启动恢复验证 |
| 整库恢复可能覆盖其他写入 | 仅在封闭发布窗口且证明无后续提交时自动恢复；发布后默认阶段恢复 |
| 历史旧备份缺指纹或原始目录已经被替换 | 不收养不可信基线；缺证据明确标记，默认完整初始化 |
| 阶段函数内部有多次 commit | 逐阶段证明幂等与输出凭据后才能跳过，不仅依赖 succeeded 标记 |
| 多任务争用资源和过期任务反复构建 | 优先级、依赖、generation/revision 栅栏及有限重试共同约束 |
| 范围缩小漏掉跨组/跨年影响 | 与完整重建对账，不能证明闭包时保留有原因的 full fallback |
| 原 HTTP 500 无法复现 | 交付诊断覆盖，保留原事件未证实状态，不猜测已修复 |
| 238 条记录缺外部证据 | 分类和影响可完成，无法证明的关联保留 unknown |
| 源版本增加磁盘占用 | 复用不可变来源、写入前检查空间；清理策略另行提出，不自动删除恢复点 |

完整交付须同时满足：

1. 输入、事实、基线可追溯，故障窗口恢复有实测证据，旧目录兼容边界明确。
2. 增量/noop/初始化/reconcile/阻断关系和各层回退均可解释，历史迟到记录不丢失。
3. 发布后可恢复任务失败不引起整库回滚；旧任务不会污染新事实，失败尝试可追踪。
4. 关键统计不被封面任务排空阻塞，性能结论有同条件原始样本。
5. played 与全量治理范围分别可见，33/238 样本完成分类及可证明修复，剩余 unknown 有明确结论。
6. 用户能区分数据更新、统计准备和质量事项，刷新与重启不丢失运行结果。
7. 真实副本对账、故障恢复、API、浏览器及默认完整本地全栈门禁通过；未解决历史事件和外部条件单列。

本规划完成不以所有 warning 归零为目标，也不把文档审计、局部测试或副本成功写成正式主库已迁移或生产已部署。
