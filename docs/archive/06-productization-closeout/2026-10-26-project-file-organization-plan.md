## 执行阶段与依赖

顺序为P0 → P1 → P2 → P3 → P4 → P5 → P6 → P7。一个负责人串行处理共享路径，不启动并行研发或额外工作树。P2完成即可单独确认空间清理结果，不让后续代码整理使该结果一直开放。

### P0：确认执行对象与运行基线

1. 复核Git状态和当前分支，保护新出现的无关改动；复用当前目录，不执行整树reset、clean或stash覆盖。
2. 复核两个删除目录的真实路径、大小和打开文件；检查是否有导入、快照维护、构建或验收任务正在使用它们。活动任务先正常结束，不中断事务或删除活动锁。
3. 记录本地服务的监督入口、父子关系、端口、工作目录和必要的非敏感环境覆盖，特别是预热模式与数据库路径。读取配置时不导出整份环境或凭据。
4. 核对当前正式数据库、来源和启动配置不指向待删目录；如发现新的活动输入，先按原用途迁出并更新消费者。
5. 将最小清单写到 `data/maintenance/project-file-organization-20261026/`，同步忽略规则。记录目录级计数、删除范围、服务身份与操作时间即可，不复制16 GiB材料，不给全库和所有证据文件生成哈希。

完成条件：两个删除对象和保留范围明确，当前服务可正常重启，无其他正在使用待删材料的任务。出现新漂移时只处理具体依赖，不重开历史业务验收。

### P1：解除日常服务对output的依赖

1. 建立 `data/logs/` 并加入Git忽略规则；Docker已有整目录排除规则，保持该边界。
2. 核对 `scripts/start_daily.py` 本身继承调用者标准输出的现状，优先调整本地启动重定向和维护说明。只有现有方式无法稳定使用时才修改启动脚本；不为日志迁移新增守护进程框架、调度器或日志平台。
3. 向已核验的日常监督入口发送正常退出信号，等待其所属后端、前端退出及端口释放，不停止其他服务，不对运行中的SQLite文件手工checkpoint或覆盖。
4. 按原端口、原运行配置启动，日志定向到 `data/logs/`。复核后端、前端可访问，且新进程不再打开旧output日志。
5. 源码整理期间继续使用已有前端构建；最终构建切换在P6单独完成，避免长时间停服和构建覆盖正在使用的dist。

完成条件：本地服务恢复、旧output无运行消费者、新日志能正常写入。若重启失败，在保留的数据和构建上解决启动问题，暂不执行P2；不通过删除旧恢复点来排障。

### P2：清除已收口材料与旧缓存

1. 再次核对两个绝对目录无活动消费者；按删除清单整体删除本地 `output/` 和 `data/backups/`，不改用移到废纸篓或另建整份归档冒充空间回收。
2. 在没有对应检查进程时清理三类工具缓存。保留依赖环境、浏览器CLI记录和正式数据。
3. 记录删除对象数、目录内容大小与操作前后磁盘可用空间；核对正式数据及原始来源仍在原位置、服务可访问。无需执行数据库深度扫描或恢复演练。
4. 记录原始日志、截图及联合恢复点已按用户决定删除、不能再按历史路径恢复。历史报告的当时结论和失败记录保留，不将“收口后清理”改写为“从未存在”或“已另存”。

完成条件：既有两目录内容清理完成、无已删除文件仍被进程占用、正式数据保留且本地服务正常。可用空间未按逻辑大小等量增长时，如实报告APFS/快照影响，不追加全盘清理。
