# 合作曲排行修改计划

创建日期：2026-10-02。状态：IN_PROGRESS，正在实现与验收，尚未提交或部署。

适用入口：播放分析 → 播放记录 → 探索与品味 → 合作曲排行。本文确定建议实施的口径、改动范围和验收条件；实施时再同步当前参考规则。

## 1. 修改目标与现状

合作曲应由已经记录的有效曲目署名判断，标题没有写 feat. 的歌曲也能自动进入排行。歌曲、专辑、艺人三个榜和播放占比必须使用同一份合作事件集合，避免各自识别、结果不一致。

当前实现位于 `backend/domains/playback/records_discovery.py`：

- `_feat_lover_track()`、`_feat_lover_album()` 通过 `_has_feat_marker()` 检查歌名。
- `_feat_lover_artist()` 同样先检查歌名，再限定 `role = featured`。
- 歌曲榜按歌名和艺人名分组，尚未直接使用当前 L2/L3 的稳定歌曲身份。
- 页面通过 `/api/analysis/records` 读取持久结果快照，修改计算函数后仍需更新缓存合同并重建快照。

2026-10-02 的服务器只读检查已确认如下实际数据：

| 曲目 | 有效署名 | 旧标题判断 | 修改后的预期 |
|---|---|---|---|
| We Found Love | Rihanna、Calvin Harris | 不识别 | 计入合作曲，两位艺人获得参与次数 |
| Hold Me Closer | Elton John、Britney Spears；当前均为 primary | 不识别 | 计入合作曲，不因两位都是 primary 而漏算 |

Spotify `artists[]` 已回填不等于这个板块已改用有效署名。此次修复消费逻辑，无须再次采集全库 Spotify 数据。

## 2. 建议采用的产品口径

### 2.1 什么是合作曲

一次有效逻辑播放所属曲目的有效署名，经过 canonical artist 身份合并后，包含至少两位不同艺人，即计为一次合作曲播放。

有效署名继续由 `backend/domains/metadata/track_credits.py` 唯一解析：原始署名与标题识别兜底 → Spotify 自动署名补充 → 人工覆盖 → canonical 身份去重。本模块不再解析标题，也不直接拼接 Spotify 原始数组。

- 两位共同主唱、主唱加客串、三位及以上参与者均适用。
- Tanya Chua 与蔡健雅等已关联到同一 canonical artist 的别名只算一位。
- 乐队或组合按其艺人实体算一位，不展开成员。
- 只有一位有效艺人时不计入，即使标题含 feat.；元数据缺失时不自行猜测或产生逐条审核任务。
- 结果表示“按当前已记录署名识别的合作曲”，不宣称覆盖现实中所有参与者。

### 2.2 三个排行与占比

| 输出 | 纳入范围 | 计数单位 |
|---|---|---|
| 歌曲榜 | 实际发生合作曲播放的歌曲，按当前 L2/L3 歌曲身份汇总 | 每个有效逻辑事件一次 |
| 专辑榜 | 按现有 album project membership 归属这些合作事件 | 每个事件对同一专辑项目至多一次 |
| 艺人榜 | 合作事件的全部有效参与艺人，不限定 primary/featured | 每个事件对同一 canonical artist 至多一次 |
| 合作曲播放占比 | 合作逻辑事件数 ÷ 同一过滤范围的全部有效逻辑事件数 | 先精确计算，仅展示时保留一位小数 |

艺人榜改为“合作曲参与艺人”，主唱和客串均获得参与次数。这是有意调整当前“只统计 featured”的口径；实施时必须同步 `playback-stats-rules.md` 的 R31b，而不是让旧规则与新实现并存。

同一次合作曲播放可以分别贡献给两位艺人，因此艺人榜次数相加允许超过合作曲播放总次数；歌曲总播放及占比不能因艺人展开而增加。

### 2.3 独唱版与合作版合并

先按实际播放所属曲目的署名判断是否合作，再应用 L2/L3 分组。不能把组内出现过合作版，解释为整个歌曲组的所有播放都是合作曲。

验收例：独唱版 Karma 播放 10 次，含 Ice Spice 的合作版播放 3 次。即使 L3 将二者汇总，合作曲榜中该歌曲只计 3 次，Taylor Swift 和 Ice Spice 在本板块各计 3 次，分母仍含全部 13 次。

## 3. 后端实施设计

### 3.1 一次构建共用合作事实

在 `compute_discovery_records()` 内准备一次调用范围的合作事实，传给三个排行计算函数。复用已经加载的事件、歌曲、专辑和艺人 frame；有效署名只对本次参与的代表曲目 ID 批量读取或复用，不为每条播放查询数据库。

事实至少包括：可靠的代表曲目键、规范艺人成员集合、合作曲标记，以及可与各 frame 对齐的逻辑事件键。

现有 loader 的 `track_id` 可能表示 L1 身份，艺人展开使用 `representative_track_id`。实施前应核对 standalone 和 yearly preloaded 两条路径，使用它们实际消费的代表曲目键连接有效署名；不能将 source track ID、L1 ID、L2/L3 聚合 ID 混用。合作判断发生在 L3 汇总之前，并复用当前身份/播放 loader 合同。

逻辑事件去重沿用 `assign_logical_event_id()` 的 `_logical_event_id`。单个原始 `play_id` 可能产生多个逻辑事件，因此禁止只按 `play_id` 去重；也不能把不同 frame 的行号直接当成可关联的事件 ID。需要补齐事件键时，在艺人展开前建立并保持一致。

连接不可用的预加载路径，只有提供了可靠曲目键和 canonical 艺人身份时才能复用其署名事实。缺少必要身份信息时保持不可判定，不回退到标题正则或仅凭展示名称猜测。

实现以批量查询、map/merge、groupby 和去重为主；不增加热路径整表重复扫描、逐播放循环或 `apply(axis=1)`。共享事实随单次构建结束释放，不引入新的全局缓存。

### 3.2 调整三个聚合函数

- 歌曲榜使用筛选后的 `track_frame`，按 canonical track key 汇总，输出稳定 `entity_id`、`entity_type` 及展示署名。同名不同曲保持独立，详情链接和封面使用现有实体解析，避免依赖歌名查找。
- 专辑榜使用同一合作事实筛选 `album_frame`，保留现有 L2/L3 项目归属及 `include_compilations` 参数；不因合作艺人参与而新增专辑所有权。
- 艺人榜筛选合作事件后保留所有有效艺人，按逻辑事件与 canonical artist 去重；删除本模块对 `role = featured` 的筛选，不修改署名角色本身。
- 排序统一为播放次数降序、精确时长降序、稳定实体键升序，先完成全部候选排序，再截取现有 Top N。
- 时长并列裁决复用 `records_duration_frame()` 等现有收听区间事实，按相同合作范围筛选；不把 fan-out 后重复行当成额外时长。
- 有有效播放但没有合作事件时保留 0% 摘要与空排行；没有有效播放时使用现有空数据处理，不产生除零结果。

`_has_feat_marker()` 若经引用检查确认仅用于旧合作曲识别，可移除；导入阶段用于补充原始署名的标题识别继续保留。

### 3.3 缓存和共用消费者

`backend/services/analysis_records_service.py` 的 `PLAYBACK_RECORDS_SORT_CONTRACT_VERSION` 已参与 LRU 及持久快照请求键。此次修改升级该合同版本，使旧标题筛选结果不能作为新口径的精确结果继续命中。

检查 `analysis_snapshot_revision.py` 已覆盖有效署名与身份变更的实际依赖：人工添加、移除、身份合并和 Spotify 自动署名变化都应触发新 Records 结果。优先复用现有修订与维护机制，仅在发现缺失依赖时补齐，不新增独立修订体系。

年度总结也会复用 Records builder。预加载路径必须得到相同合作判断，并检查现有年度产物的 builder/cache 版本依赖；若不会因此次合同变化失效，应更新对应版本。年度范围、其他纪录和既有历史产物不应被静默改写；新的受控生成使用新口径。

默认 lifetime、近 4 周、近 6 个月快照通过现有私有维护任务重建；L3、其他时间范围沿用现有显式 prepare 流程。GET 保持只读，不能为消除旧结果而恢复同步冷构建。

## 4. 前端和兼容性

修改 `frontend/src/features/analysis/records/DiscoverySection.tsx`：

- 主标题保留“合作曲排行”，英文副名改为 Collaboration Ranking。
- 简短说明采用“两位及以上艺人共同署名的歌曲，按有效播放次数排行”。
- 艺人视图明确显示“合作曲参与艺人”，说明次数代表其参与的合作曲播放。
- 保留现有歌曲、专辑、艺人切换及占比摘要，不增加来源审核、证据链接或新的管理表单。
- 歌曲行使用明确的歌曲身份、封面和完整展示署名，核验手机和桌面链接一致。

现有 `discovery.feat_lover.track/album/artist` 响应结构和 `feat-ranking` 锚点可继续使用，降低对前端类型、年度消费和历史深链的影响；内部旧命名不影响新口径。只有现有行字段不能承载稳定身份或艺人列表时，才做必要的兼容字段补充并同步类型。

## 5. 实施阶段与完成条件

| 阶段 | 工作 | 完成条件 |
|---|---|---|
| S1 | 在数据库副本上记录旧结果，确认事件、代表曲目及 canonical 艺人键；固定回归案例 | 能解释实际漏算，三个 frame 的事件可正确对应 |
| S2 | 共用合作事实，替换三个筛选与聚合，补稳定歌曲身份和去重 | 无标题标记也可计入；独唱版不误计；次数守恒 |
| S3 | 更新缓存合同、检查修订依赖、接通年度预加载路径 | 新快照命中新口径，人工署名变化后可更新 |
| S4 | 调整页面说明、完整署名和实体链接，同步规则文档 | 两端显示与统计语义一致，无新增后台工作 |
| S5 | 专项测试、实际数据库前后对比和浏览器验收 | 下表案例全部通过，其他 Records 模块结果不变 |
| S6 | 按项目流程提交与发布，受控重建生产快照并复核 | 服务器实际页面与新接口均使用新规则 |

主要文件：`records_discovery.py`、`analysis_records_service.py`、`DiscoverySection.tsx`；按检查结果涉及 `records_output.py`、年度缓存版本或分析快照依赖。测试更新现有 Records 排序/预加载/快照及页面测试，必要时新增专门的合作曲统计测试文件。

## 6. 验证案例与验收标准

| 案例 | 必须满足的结果 |
|---|---|
| We Found Love，无 feat. 标记 | 计入合作曲，Rihanna 和 Calvin Harris 各获得该事件一次参与 credit |
| Hold Me Closer，两位 primary | 同样计入，两位共同主唱都进入参与艺人榜 |
| 三位参与艺人 | 歌曲/占比计一次，每位艺人各一次 |
| Tanya Chua 与蔡健雅别名重叠 | 规范身份去重；仅一个实际艺人不构成合作 |
| 标题有 feat.，人工已移除客串 | 按最终有效署名判断，不因标题重新纳入 |
| 标题无合作标记，人工补入或移除艺人 | 次数与占比随有效署名和快照更新变化 |
| L3 合并独唱版与合作版 | 仅合作版实际事件计入，不能把整个作品组播放 credit 给客串艺人 |
| 同名不同歌曲、相同时间戳或重复源 play_id | 正确区分歌曲及逻辑事件，不误合并或重复计数 |
| 合作曲跨来源专辑及精选集 | 按既有项目归属及过滤统计，不改变专辑所有权 |
| 时间范围、静态/动态门槛、连续播放合并 | 分子分母使用相同过滤和逻辑事件集合 |
| 0 次合作、0 次有效播放、缺少可靠署名 | 无崩溃、无猜测、摘要和空态符合既有合同 |
| standalone 与年度预加载相同范围 | 合作事件数、三个榜及占比相同，年度范围不越界 |
| 修改后重建快照、再编辑署名 | 旧版本不继续命中 exact；新修订能够发布正确结果 |

真实数据对比使用 SQLite Online Backup 副本，固定过滤配置和代码版本，记录旧/新合作播放次数、占比、三个 Top N、新增/移除样例及耗时。除本板块和相关展示字段外，其他 Records 结果应保持一致。验收不能只看歌曲是否进入 Top N：播放较少的歌曲可能仍在榜外，应核对筛选资格与完整聚合结果。

运行针对性后端/前端测试及必要的快照合同测试、前端构建、文档审计和 `git diff --check`。浏览器在 Desktop 与 Phone 实际视口检查切换、占比、长署名、封面和深链。局部全栈结果标为 Partial；只有默认完整全栈必需阶段全部通过才能报告本地全栈 Pass。

## 7. 发布与回退

实施检查确认需要增量 migration 85：为 Spotify 自动署名补齐现有分析修订触发器，不改写原始播放或署名数据，也不改变搜索来源指纹。生产发布仍按项目已有 commit SHA、Online Backup、健康检查和回滚流程执行；使用现有队列构建新版本的 Records 默认快照，保持公开 GET 只读。

服务器验收必须检查新 snapshot/builder 版本、目标来源修订、服务状态，以及真实 `/api/analysis/records` 和页面展示。若结果按 Top N 截断，使用受控副本确认 We Found Love、Hold Me Closer 的筛选资格，不要求它们必然进入 Top N。对实际使用的其他时间范围或 L3 深链按现有私有 prepare 流程补建。

回退使用旧代码与旧版本派生结果，按既有联合回滚流程处理快照；不为回退删除 Spotify 回填署名、撤销人工覆盖或恢复原始数据库。源码部署、快照发布、接口和浏览器验收分别记录，全部完成后才标记生产修复完成。

## 8. 本轮范围

不引入第二元数据来源、合作关系专用表、人工核对队列或独立署名角色模型；也不调整 Billboard 艺人 credit、语言/流派规则和歌曲总播放统计。后续若需要严格区分“客串艺人”与“共同主唱”，另行讨论角色模型，本次合作曲识别不依赖该区分。
