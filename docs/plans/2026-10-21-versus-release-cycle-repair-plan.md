## 2 根因与因果链

1. **证据规则与历史恢复没有共同完成。** schema89 保留旧日期、precision=NULL 是正确的保守迁移；日级消费者随后只接受 confirmed/day。既有范围的 92 份来源维护不等于全库发行功能恢复。
2. **维护选择器缺少语义完整性判断。** 当前主写入路径已保存来源精度，但旧缓存只要封面、目录等字段完整，就不会因缺日期精度或 Album 身份进入维护。
3. **发行解析与当前专辑统计身份不同步。** 周期链通过 tracks→spotify_track_meta 的父发行和旧 release group/名称找版本；个人对比已采用 project/membership。需要逐项核对二者差异，不能假设所有查找失败都由 precision 引起。
4. **失败原因在链路中丢失。** 日期过滤、身份过滤和最终匹配失败都可能变成 release_day_unconfirmed；前端进一步补 metrics={}，既不显示 unavailable，也不展示请求错误。
5. **验收没有守住恢复能力。** 集成测试允许 comparisons 与 unavailable 合计正确就通过；前端测试接受空指标。保护了缺证不乱算，但未覆盖维护后恢复、真实覆盖率及可解释展示。

10 月 7 日报告已记录旧 Taylor 结果同时缺 Album 艺人证据，不能将所有不可用追溯为那一次日期改动，也不能改写此前验收结论。

## 3 修复后的统计与身份合同

### 3.1 对比对象与日期锚点

- 当前榜单选择器的专辑对象以对应 L2/L3 的稳定 project 身份为准。复用现有 project resolver、membership 和艺人 canonical 规则，不另建名称归并系统。
- 对项目的发行周期采用已明确的主发行来源日。只接受属于该项目、身份通过且日期合法一致的来源证据；多个来源冲突时保留冲突，不以最早日期、播放最多或同名记录代选。
- 旧名称入参保留兼容解析；唯一映射时返回解析后的稳定身份。若旧调用明确指向独立发行版本，必须保留版本与日期语义；无法唯一确定时返回歧义原因，不能静默改成主版本。
- 实施第一个阶段需用既有成功样本固定“项目对比/明确版本对比”的输入到锚点对照表。若当前选择器确实暴露独立版本，则保留该能力；需要产品口径变化时先列出具体前后差异再决定，不借修复重定义指标。
- L2/L3 对比使用各自有效 membership；合作署名、艺人别名和来源专辑名不应造成遗漏、重复或错误归属。普通榜单与发行周期必须解析到同一个目标实体。

### 3.2 日期与指标

- confirmed/day 且身份和版本可确定时才执行按发行日对齐。legacy、year/month、缺失、异常、不一致及来源冲突分别说明原因，不使用首次播放日或其他版本日期补齐。
- 六项指标保留现有定义，包括发行窗口与完整结束榜单周边界；不使用普通对决的全历史最高排名替换周期窗口最高排名。
- 真实 0、未在窗口上榜、窗口内无播放、不适用、缺证和请求失败分开表达。实现前核对各指标的数据依赖，防止一个空时间线使已有可证明的独立指标被不必要清空；如发现这类缺陷，先补定向失败用例再修改。
- 日期证据必须显式传递，不能仅因值已变成 pandas Timestamp 就视为已确认来源。

### 3.3 读取与维护分工

对比读取只消费已安装证据及 exact-ready 榜单上下文，不因打开表格联网补证、写库、冷建完整榜单或排队。私有和公开读取对同一事实给出一致结果。现有读取中的条件式外部补证迁入明确维护路径，不能让私有页面碰巧联网成功成为恢复条件。

## 5 历史数据补证与持续维护

### 5.1 清单与来源请求

先只读枚举已播放来源、项目关联、曲目元数据及选择器实际引用的已知 Spotify Album ID，按稳定 ID 去重。全缓存也需筛查，但不再使用的孤立缓存单列，不为清零指标自动联网抓取。清单包含：引用对象、日期状态、艺人证据状态、版本/项目关联、阻塞原因及预期恢复条件。

同一个官方 Album 响应中的日期、precision 和有序 artists 一次处理，不分别运行两个互不衔接的日期/艺人脚本。复用现有 Provider 与持久化函数，优先只获取所需证据；不因补日期重抓全部曲目分页、封面或重建身份关系。

沿用有界批处理，每批不超过现有日期维护的 200 个显式 ID，内部请求遵守 Provider 限额。处理已有清单的所有批次，记录进度与失败 ID，能够重放已取得响应；不为此次修复另造调度平台。来源响应、数据库和运行记录保留在 ignored 的私有证据目录。

### 5.2 安装规则

- 每个来源的日期与 precision 成对保存，同时保留 Album 艺人来源；分项拒绝和事务结果可追溯，不把整批 HTTP 成功当作证据安装成功。
- 缺失/异常刷新不擦除可靠旧值；日期冲突、艺人 ID 冲突和无法唯一解析的身份进入审核，不自动批准关联。
- 同步可证明的非人工项目日期精度。若官方证据纠正 legacy 月日，必须明确处理非人工项目的旧日期锚点：唯一且符合现有项目规则时在维护阶段同步；有多个来源或冲突时保留审核，不能只更新 source 后继续使用旧项目日期。人工项目日期、membership 和署名决定保持。
- revision 失效覆盖实际变化的证据与受影响派生消费者，按现有维护流程发布并复验 exact-ready；不让前端继续命中补证前的空结果。不得通过关闭只读门禁或强复用旧快照绕过缺失。
- 当前未知、已确认到年/月、来源失败、冲突待审是不同状态；只有可自动恢复项进入有界重试。无新增证据不反复刷新已确认粗日期或人工审核项。

### 5.3 副本与正式库

先在 Online Backup 副本安装证据，核对差异后再应用正式库。不能将较旧的整库副本覆盖回当前库；按已验证清单应用证据，检查输入 revision/受保护事实漂移，重新准备受影响快照。保留应用前后备份、清单及每批结果，发生源漂移立即停止该批并重新核对。

本地结果不自动用于生产：后续发布阶段重新取得生产基线，复用可以证明仍适用的来源响应，保留生产独有任务、设置和人工决定。

## 6 API 与页面行为

下列是语义分类，具体字段与枚举在 P1/P3 复用现有模型确定，避免另建并行协议。

| 状态 | 页面表达 | 后续动作 |
| --- | --- | --- |
| ready | 显示可证明指标；真实零为 0，单项无排名说明未上榜 | 正常比较 |
| legacy / missing date evidence | 缺少已确认的发行日 | 明确维护补证；页面读取不触发任务 |
| confirmed year/month | 来源仅精确到年/月，不能按发行日对齐 | 保留已有精度，不伪造 day |
| artist identity unconfirmed | 专辑艺人身份尚未确认 | 补来源或人工审核 |
| release ambiguous / conflict | 无法确定发行版本或来源日期冲突 | 保留可审核信息，不自动代选 |
| entity not found | 未找到对应项目/发行 | 检查旧名称兼容映射，不误报日期问题 |
| snapshot unavailable / request failed | 当前统计暂不可用或请求失败 | 保留全部对比列，提供读取重试与真实原因 |

保持请求队列顺序和对象身份，部分成功不影响其他列；loading、error、unavailable 与 ready 各自可见。沿用 TanStack Query/queryKeys、取消和过滤指纹；维护成功后通过现有失效路径更新结果。

不新增对外维护按钮或恢复已退役的发行周期详情页签。公开端可展示原因，不暴露凭据或内部维护数据。手机沿用互斥 presentation 和 44px 触控目标；多列表格只在自身容器横向滚动。

### 7.3 测试停止条件

本轮规划仅运行文档审计与 diff 检查。实施阶段先做上述受影响回归，累计代码固定后集中做一次必要整体验证及前端构建；正式提交/发布执行已有必需 hooks、CI 和发布门禁。没有统计差异、新失败或明确覆盖缺口，不重复全站、跨环境或资源实验。结果只按实际覆盖命名，不将局部成功称为完整全栈 Pass。

## 8 发布与回退

代码固定后再根据本地副本演练确定发布包：先准备兼容的状态/读取代码、来源清单及派生快照，核对 Online Backup 和输入漂移；获得发布授权后按现有 commit SHA、CI、三模式门禁、健康与联合回滚流程执行。保持外部入口和身份边界。

应用失败时停止后续批次并保留旧可用结果；记录已安装批次和来源变化，不通过删证据、清空缓存或强制重启掩盖失败。需要回退时使用验证过的代码、数据及派生状态配套恢复，不能只回退代码却继续消费不兼容事实。恢复前核对应用后的新增播放和人工修改，避免直接恢复整库造成数据损失。

正式验收在正常单用户负载下完成代表请求和交互；不追加生产压力流量、OOM 实验或另一套性能门槛。
