# 播放记录全板块统计正确性与稳定排序修复规划

> 创建日期：2026-08-30
> 状态：IMPLEMENTED；真实 API/浏览器内容验收因冷计算阻塞，待低干扰窗口复验
> 适用范围：`/analysis/records` 的 5 个页面板块、20 个可见模块，以及其 API-only 播放记录模块
> 当前实现：后端统计/排序、前端精确值、自动化测试、真实数据库只读探针和文档已完成；真实 API/浏览器内容验收未闭环
> 当前规则：[`../reference/playback-stats-rules.md`](../reference/playback-stats-rules.md)

## 1. 目标与问题边界

本规划处理播放分析中的“播放记录”页面，不改变 Billboard 周榜的周边界、canonical track、album project membership、有效播放过滤或艺人有效署名的总体定义。目标是让每个记录模块同时满足：

1. 统计只使用与页面筛选范围一致的有效逻辑播放事件；需要个人历史序号的模块明确使用完整历史。
2. 先在完整候选集上计算精确指标和完整排序，再应用 Top 50 或模块上限。
3. 主要指标相同时，使用有业务意义的第二指标，最后使用稳定实体键或规范化文本裁决；不得依赖 DataFrame 输入顺序、index 或截断后的偶然顺序。
4. 展示值可以取整，但排序和排名必须保留 `ms_played` 的精度。
5. 后端 API、前端本地切换排序、回归测试和文档使用同一契约。

已确认的重点风险：

- `/analysis/records` 按年度或自定义周期筛选后，播放里程碑仍被文案标记为 lifetime，可能把周期内第 N 次误报为个人历史第 N 次。
- 艺人 fan-out 在加载后丢失 `role`，合作曲排行无法区分 primary 与 featured，可能把主艺人污染到“合作艺人”榜。
- 单实体只有一天播放时，最长连续播放天数分支把总时长写成 `0`。
- 工作日偏好先生成 rank 再排序，第一名的 rank 可能不是 1。
- 单日总量记录以取整后的小时参与排名，两个实际时长不同的日期可能被错误视为同值。
- 多个 `idxmax()`、`head(50)` 或单键 `sort_values()` 路径没有完整二级/后续排序；相同输入在重建、分页或输入乱序后可能换位。

## 2. 统一排序契约

共享后端 helper 负责稳定排序、完整候选集截断和最终连续 rank。排序键中的 `total_ms` 使用原始毫秒；`total_hours`、百分比等仅用于展示。所有缺失排序值置后，最后的 stable key 不得是当前行号。

| 页面/模块 | 主排序 → 二级排序 → 后续裁决 |
|---|---|
| 高光时刻·单日巅峰（次数） | 播放次数 DESC → 当日总毫秒 DESC → 日期 DESC → 实体稳定键 ASC |
| 高光时刻·单日巅峰（时长） | 当日总毫秒 DESC → 播放次数 DESC → 日期 DESC → 实体稳定键 ASC |
| 高光时刻·单日总量 | 当前切换指标 DESC；次数模式为 `total_plays`，时长模式为 `total_ms` → 另一项指标 DESC → 日期 DESC |
| 高光时刻·播放里程碑 | 播放序列时间 ASC → 稳定 `play_id` ASC；周期筛选只筛选结果，不重置 lifetime ordinal |
| 高光时刻·最快里程碑 | 达成天数 ASC → milestone 日期 ASC → 首次日期 ASC → 实体稳定键 ASC |
| 高光时刻·连续播放马拉松 | run 长度 DESC → run 总毫秒 DESC → run 结束时间 DESC → 实体/起止时间稳定键 ASC |
| 个人王朝·每日冠军次数 | 冠军日数 DESC → 冠军日播放次数 DESC → 冠军日毫秒 DESC → 实体稳定键 ASC |
| 个人王朝·月度统治 | 冠军月数 DESC → 冠军月播放次数 DESC → 冠军月毫秒 DESC → 实体稳定键 ASC |
| 个人王朝·年度统治 | 年份 ASC 展示；同一年先按播放次数 DESC → 毫秒 DESC → 实体稳定键 ASC |
| 个人王朝·连续冠军天数 | 连续天数 DESC → 连续段播放次数 DESC → 连续段毫秒 DESC → 结束日期 DESC → 实体稳定键 ASC |
| 长线陪伴·最长连续播放天数 | 连续天数 DESC → 实体总播放次数 DESC → 实体总毫秒 DESC → 结束日期 DESC → 实体稳定键 ASC |
| 长线陪伴·最长陪伴跨度 | 跨度天数 DESC → 播放次数 DESC → 毫秒 DESC → 最近日期 DESC → 实体稳定键 ASC |
| 长线陪伴·沉睡后回归 | 间隔天数 DESC → 播放次数 DESC → 毫秒 DESC → 回归日期 DESC → 实体稳定键 ASC |
| 长线陪伴·最活跃月份 | 活跃月份数 DESC → 播放次数 DESC → 毫秒 DESC → 实体稳定键 ASC |
| 时间习惯·时段统计 | 每个小时独立选冠军：播放次数 DESC → 毫秒 DESC → 实体稳定键 ASC；最终按小时 ASC 展示 |
| 时间习惯·月度巅峰 | 每月独立选冠军：播放次数 DESC → 毫秒 DESC → 实体稳定键 ASC；列表按播放次数 DESC → 毫秒 DESC → 月份 DESC → 稳定键 ASC |
| 时间习惯·年度巅峰（API-only） | 每年独立选冠军：播放次数 DESC → 毫秒 DESC → 实体稳定键 ASC；最终按年份 ASC 展示 |
| 时间习惯·深夜峰值日 | 深夜精确占比 DESC → 深夜播放次数 DESC → 全部播放次数 DESC → 日期 DESC |
| 时间习惯·深夜轨迹 | 趋势图按月份/季度 ASC；“最高周期”使用未取整占比 DESC → 深夜次数 DESC → 总播放次数 DESC → 周期 DESC |
| 时间习惯·工作日偏好（API-only） | 播放次数 DESC → 每活跃日平均播放次数 DESC → 周一至周日序号 ASC |
| 时间习惯·跨年时刻（API-only） | 跨年播放次数 DESC → 总毫秒 DESC → 跨年周期 DESC；周期内 Top 曲目/艺人按次数 DESC → 毫秒 DESC → 规范化名称 ASC |
| 探索与品味·发现日 | 新发现数量 DESC → 首次日期 ASC |
| 探索与品味·最长不重复序列 | 按 `ts, play_id` 的确定性逻辑序列计算；结果为单一摘要行 |
| 探索与品味·专辑全碟回放 | 完整回放轮数 DESC → 总播放次数 DESC → 总毫秒 DESC → 专辑 project 稳定键 ASC |
| 探索与品味·合作曲排行 | 合作播放次数 DESC → 毫秒 DESC → 实体规范化名称/稳定键 ASC；艺人榜只使用 `role=featured` |
| 探索与品味·同名异曲 | 不同艺人数 DESC → 总播放次数 DESC → 规范化歌名 ASC → 原歌名 ASC；组内艺人按播放次数 DESC → 毫秒 DESC → 艺人名 ASC |
| API-only 行为记录 | 快进率/Shuffle 率/平台切换等比率先使用精确比率，再按样本数、计数、日期和稳定名称裁决；平台总榜为播放次数 DESC → 平台名 ASC |

实体 stable key 的优先级为 canonical track/project/artist ID；没有 ID 时才使用规范化文本 tuple。艺人 fan-out 展开同一逻辑播放时，所有依赖顺序的记录都使用稳定逻辑事件 ID，不能把同一播放的另一条署名行当成中间播放。

## 3. 分阶段实施

### Phase 0：冻结基线与失败测试

- 记录 HEAD、dirty worktree、数据库路径、schema、播放事实数量/毫秒总量和当前筛选参数。
- 用合成帧复现四类明确计算错误、精度截断和输入乱序导致的换位。
- 增加共享排序 helper、后端模块和前端本地排序的回归测试；测试必须检查排序不依赖输入顺序。

### Phase 1：后端统计口径修复

- 在周期过滤前保留 standalone 的完整历史事件帧，传给播放里程碑；Yearly Review 已注入的年度预加载帧维持原有年度语义。
- 保留 artist effective credit 的 `role`，合作艺人榜缺少角色时安全返回空集而不是发布污染结果。
- 修复单日连续天数的单日分支，使用真实播放次数、毫秒和小时展示。
- 为无 Top 5、长线、跨年、平台、深夜和发现模块补齐缺失输入的安全回退和确定性序列。

### Phase 2：统一排序与精度

- 新增共享 `sort_and_limit` / `select_period_winners`，所有候选先完整排序，再截断并重新生成 rank。
- 将单日总量内部排序改为 `total_ms`，API 保留 `total_ms` 供前端时长切换使用，显示继续使用一位小数小时。
- 将每日/月度冠军的周期 winner 选择与最终实体榜排序分离，周期内使用播放次数、毫秒和稳定实体键。
- 前端时长榜和深夜最高周期使用精确字段重排，保留旧 payload 没有精确字段时的兼容回退。
- 增加排序契约版本，避免长生命周期进程继续服务修复前的 LRU payload。

### Phase 3：完整验证

- 运行后端播放记录定向测试、unit、contract、ruff/compileall；运行前端播放记录测试和 build。
- 在真实数据库上固定同一过滤参数和 revision，检查事件/实体帧规模、关键模块非空性、Top N 前完整候选排序和排序违规计数。
- 运行 `/api/analysis/records` 的 lifetime、年度和自定义范围对账，确认 lifetime 里程碑不随页面范围重置。
- 以 desktop、compact 和 390px phone 视口检查 5 个页面板块、20 个模块的错误态、分页/切换和横向溢出。
- API 或服务受已有进程/冷构建影响时，只报告已执行的源码、测试和数据库证据，不把局部绿灯描述成整站 Pass。

### Phase 4：文档、提交与回滚

- 更新当前规则、文档地图、实施计划和交付报告；计划完成后标记为 IMPLEMENTED。
- 只 stage 播放记录相关源码、测试和文档；保留其他 dirty 文件，提交前执行 `git diff --cached --check`。
- 不修改原始 `plays`、`tracks`、`track_artists` 或 canonical identity 数据；回滚只需回退代码和排序契约版本，必要时清理对应进程缓存。

## 4. 验收门槛

| 门槛 | 通过条件 |
|---|---|
| 统计口径 | 四类已知 bug 有失败前测试、修复后通过，且完整历史/周期语义明确 |
| 完整性 | 每个 Top N 模块在截断前排序；合作艺人、专辑 project 和发现实体没有无声丢失 |
| 稳定性 | 合成帧随机乱序后每个列表的实体顺序和 rank 完全一致 |
| API | `total_ms` 等精确排序字段可安全序列化，既有旧字段兼容；响应不出现 NaN/NaT |
| 前端 | 本地排序与后端排序一致，时长和深夜比较不使用取整显示值 |
| 工程 | 定向、unit、contract、前端 test/build、docs audit 和 scoped commit 结果可追溯 |
| 外部状态 | 未执行的真实 API、浏览器或部署验收必须明确标为 Partial/Blocked，不得以源码证据替代 |
