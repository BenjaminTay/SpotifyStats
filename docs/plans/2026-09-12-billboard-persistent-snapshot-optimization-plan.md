范围：Billboard 周榜、年榜、总榜及其共享确定性计算链路。目标是让榜单 GET 在数据和统计规则没有变化时直接读取磁盘快照；播放导入、元数据治理、统计设置或规则版本变化后，由后台任务生成新快照，旧快照在新快照完成前继续作为 last-known-good（LKG）返回。

## 当前基线

- 年榜通过进程内 `lru_cache` 保存，进程重启、浏览器刷新或 LRU 淘汰后会重新计算。
- 年榜当前会用超大 `top_n` 扫描完整周榜候选；生产曾出现约数分钟的首次构建，前端默认请求超时无法覆盖。
- 年榜页面收到可用年份后会预取全部年份，多个冷请求可能同时争抢 CPU 和 SQLite。
- 周榜预聚合表是中间数据，不等于最终 API 响应快照；总榜仍会在请求中重新组合周榜、power scores 和 summaries。
- 当前生产镜像需要先与仓库的 Billboard 聚合 builder 版本一致，否则 `_try_load_from_agg()` 会拒绝既有聚合并回退原始播放记录扫描。

## 目标契约

1. GET 优先读取持久化 exact snapshot；命中不执行 Billboard DataFrame 计算。
2. exact snapshot 不存在但有旧版本时，GET 先返回旧版本，后台任务负责重建；没有任何快照时才允许同步冷建。
3. 周榜、总榜、完整 Billboard staged 输出和年榜按请求参数精确隔离，参数、播放事实 revision、元数据 revision、聚合 builder、榜单语义版本变化会选择新 key。
4. 无数据变化的应用重启不触发全量重建；后台启动检查只做精确快照命中，不重复计算。
5. NOOP 导入不触发重建；真实导入、元数据/版本治理、统计设置和聚合规则变更完成提交后，异步排队一次去重的快照重建任务。
6. 快照写入采用压缩、事务替换和损坏回退；公共只读面只能读取既有 sidecar，不得因 GET 创建或修改缓存文件。
7. 前端不再因为首个年榜响应自动下载全部年份；切换到某年时才请求该年份。

## 验收门槛

- 相同数据库、相同参数、相同 revision 下，首次计算与持久化命中 JSON 等价。
- 进程重启后 exact hit 不调用 `_load_and_rank`；缓存损坏时删除/跳过该行并可安全 fallback。
- 修改设置或导入数据后，GET 不会把旧 key 当成新 key；有 LKG 时先快速返回，后台任务完成后新 key 命中。
- NOOP 导入不新增 Billboard rebuild job。
- 年榜页面初次加载只请求默认/当前年份，不自动发起所有年份请求。
- 生产 `/api/health`、默认周榜、总榜、年榜指定年份在 30 秒内返回；冷建耗时只能作为后台任务指标，不得成为普通 GET 的常态。
