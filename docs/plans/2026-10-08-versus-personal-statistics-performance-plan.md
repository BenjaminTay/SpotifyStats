## 1. 目标与范围

用户确认迟迟才出现的是对决记分牌的“个人播放”：总播放、总时长、日均播放、日均时长、单天最多播放、活跃天数和三个时间范围的个人排名。

本项交付目标：歌曲、专辑、艺人三类对决的 2–4 个对象，基础指标尽快完整出现；排名通过已发布共享结果读取；换对象、排序、切类型或过滤条件时不重复全库排名，不展示旧对象结果，不对未齐数据宣布胜负。

保留榜单成绩、走势和专辑发行周期的现有产品行为。修改范围包括其与个人统计的请求编排和记分牌消费，发行周期计算本身另行排查。完整详情统计 API 保持兼容；仅在共享统计提取和排名消费者统一所必需的范围修改。生产 OOM 的其他冷路径、Search FK 清理、全库数据审核均由原事项管理。

用户随后授权完整执行本方案直至全部阶段完成，并允许必要子 agent 和按大阶段自主 Git 提交。实现、验收、提交、推送与发布仍分别记录；正式事实不得由性能优化重写。

### 2.3 根因与必须验证的边界

1. 前端把个人统计放在榜单成功之后，基础统计又等待同一个响应中的重型排名。
2. `_ranks` 对三个时间范围调用全库 `chart_rows`，`rows_by_scope` 只存在于一个对象请求内；不同对象的结果缓存和 singleflight key 不同，不共享排名构建。
3. 排名读取经过通用榜单行生成，包含时长切片、展示元数据和完整行序列化。专辑完整统计还计算 Top 250、曲目明细与最近播放；对决不消费这些字段。
4. 桌面端隐藏未取得数据的栏目，个人请求错误缺少明确呈现；`bestIndices` 在仅一个对象有值时也可能返回胜者。分批加载必须同时修复此消费边界。

**不能直接删除排名的时长计算。** 当前播放排行按 `plays DESC → hours DESC → 稳定实体键 → 规范化名称` 排序，名次为稳定排序后的序号。优化须保留时长的排序事实，减少重复切片与展示工作；不得换成仅次数排序或自行改为 competition rank。参考[当前排序规则](../issues/2026-08-27-issue-register.md#排序规则当前实现)。

## 3. 目标架构与 API 合同

采用两条独立、可并行的批量读取路径，复用当前 Billboard 主响应：

```text
对象队列及过滤条件就绪
  ├─ 原 Billboard 对决请求 → 榜单成绩与走势
  ├─ 个人基础指标批量请求 → 目标范围统计 → 全部对象的基础行
  └─ 个人排名批量请求     → 共享精确排名发布 → 全部对象的排名行

导入/治理/设置变更或显式私有维护
  → 规范化排名任务去重 → 重型任务排他执行 → 校验并原子发布
```

### 3.1 批量接口

拟新增以下两个端点，路径在 S0 合同冻结时确定，后续实现不同时维护功能重复的端点：

- `POST /api/billboard/versus/{kind}/personal-stats`：只计算目标对象的基础指标。
- `POST /api/billboard/versus/{kind}/personal-ranks`：只读取已发布的共享排名，不计算全库排名。

POST 用于有界对象数组，与现有对决请求保持一致；两者均无写入副作用。后端 Pydantic 模型限定 `kind`、2–4 个对象、唯一身份和规范化过滤条件，拒绝任意 SQL、外部 URL、任意大批量或重复 canonical 对象。后端 public policy 与 full/showcase/dual Nginx 只增加这两个精确路由模式，不能放行整个 Billboard POST 前缀。

每个结果按稳定 `entity_key` 返回，不能依赖响应顺序与当前队列下标对齐。歌曲键来自 L1/L2/L3 聚合身份映射，专辑使用 project identity，艺人使用 canonical ID；名称仅用于展示和旧请求兼容。归并后不足两个对象时返回明确结果，不产生重复对决列。

基础响应只提供对决消费字段：

- `total_plays`、`total_hours`、`active_days`。
- `avg_daily_plays`、`avg_daily_hours`，保持当前 active_days 分母。
- `max_daily_plays`，由后端从目标事件统计计算，无需返回整条每日趋势。
- 每对象 `found/status` 与必要的缺失原因。
- 根级 `filter_fingerprint`、`source_revision`、统计合同版本与实际 lifetime 日期边界。

排名响应提供每对象 `lifetime`、`last_6_months`、`last_4_weeks` 及根级发布信息。首版不提供自定义时间段排名、小时排名或全库排名列表。`current_period` 不是对决消费字段，不新增计算。

两请求可同时发出；前端核对过滤指纹、源 revision 和合同版本。若它们遇到变更前后两个 revision，只保留当前上下文的基础结果，排名标为更新中，有限次数重新读取当前上下文；不能混用旧排名参与总分，也不能无限轮询。整体筛选或对象队列改变后旧响应不覆盖新结果。

### 3.2 基础指标的目标范围计算

提取可共享的目标聚合 primitive，避免先调用完整详情统计再裁剪。基础请求不能进入 `_ranks`、全库 `chart_rows`、`_top250_counts`、recent plays、Billboard 冷构建或外部 Provider。

每批解析所有对象，合并成员 track ID 的读取范围；SQL 加载目标事件和逻辑合并所需上下文，复用 `_scoped_play_loader` 的前序行保护。收听区间重建还需验证右侧事件截断是否需要补右邻上下文，不能假设只读目标歌曲就天然等价。前后文行只参与边界重建，不贡献目标指标。

同批共享 period bounds、有效署名和项目成员解析；按稳定实体键归属目标事件与收听区间，分别计算次数和时长。共享加载不能把不同实体的 DataFrame attrs 或 duration source 混用。

三类语义要求：

- 歌曲：代表 track ID、L1 source links 与 L2/L3 成员范围统一，验证现有 `/tracks/{id}` legacy 路径与 picker ID 的关系，不直接假设它们均为 L1。
- 专辑：使用 album project membership、canonical song keys、L3 实际版本归属及排除规则；同名异艺人分开，source album 不取代 project。
- 艺人：使用有效署名、canonical artist 与稳定逻辑事件去重，合作曲和 alias 不少算/重算；目标 duration source 必须按相同 canonical 艺人过滤。现有轻量艺人分支与已发布上下文分支加载方式不同，必须先对账，再提取共用实现。

空结果与真实 0 沿用当前统计合同；某对象不可用不使其余对象被写成 0，不导致详情空态回归。

### 3.3 共享排名发布

扩展现有 rank context service 与 Analysis store，建立版本化的统一实体排名 family，例如 `entity_rank_context_v2`。首版保持既有 `artist_rank_context_v1` 及其详情消费者兼容；新对决读取三类统一发布，不提前改写全部详情接口。

一份发布包含同一规范化过滤指纹下、三个时间范围的歌曲/专辑/艺人名次映射及边界元数据。周期窗口继续以现有 `resolve_period` 和播放覆盖时间为准，不能改成服务器当天。歌曲、专辑维度按 L2/L3 明确构建；艺人只依赖其实际统计合同，不引入无效的榜单 Top N、周起点或年份参数。精选集设置按专辑实际合同传递；如果旧详情与播放排行的参数传播存在差异，S0 用规则、fixture 和对账确定预期，单独记录必要的兼容补修。

发布 key 包含数据库 lineage、规范化参数和 builder version；source revision 覆盖播放、时长元数据、有效署名、canonical artist、曲目身份、album project、L3 归属及相关 settings revision。复用现有 revision 机制，热读取不全表哈希，也不以 TTL 判断事实有效。

构建复用现有身份聚合、时长事实及 `_sort_chart_rows`。三个范围的共有时长分片尽量构建一次后切片，保留未达次数阈值但有收听时长的事实。名次映射不经过封面、展示行、recent plays 或 Top 250 序列化。先证明等价，再优化这部分时长实现。

名次 map 应覆盖整个有效排名集合，不能从默认 100 或 Top 250 页面截取。名次键映射和排序均与公共播放排行一致，未入集合返回 null 而不是 0 或虚构最后一名。

### 3.4 一致性、容量与维护

首版排名消费只接受 **exact-ready**：缺失、损坏、不兼容或 source revision 过期返回结构化 503 `snapshot_unavailable`，基础指标仍可显示。排名不使用 LKG 参与当前胜负，不以旧名次冒充当前事实。

构建前后检查 source fence；中途漂移拒绝发布。三个范围和三类实体作为一个发布单位，事务完成后整体可见；失败保留已有有效发布。`singleflight`、队列去重按规范化上下文，不按对象 ID，重型工作进入现有 CPU gate。导入完成、署名/身份治理完成、项目/归属及设置变更后调度；检查任务完成链与 HTTP mutation hook 两条入口，避免只有通过页面修改才更新。

首轮自动维护仅覆盖当前服务端设置下 L2/L3 × dynamic/fixed 的四种有效组合；不因用户访问任意 min_ms 或间隔预建无限变体。非默认配置由已有私有设置提交/显式维护入口产生有界任务；公开请求不准备、不排队、不冷算。应用启动复用 ready；只补缺失上下文，四组合串行构建，不开启额外全库 warmup。

显式非默认配置使用独立 `entity_rank_context_custom` family；同一数据库最多存在四个不同的 pending/running target。限额检查、既有 target 去重与新增任务入库在同一 SQLite 写事务完成，跨队列并发不能突破限额。既有任务满额时仍可去重；新 target 满额或无法核验持久容量时返回 `deferred`，不假称已排队，也不退回无界内存队列。该限额不改变默认四配置的规范化去重与其他 family；默认配置在设置变更时继续允许新上下文维护，避免旧参数任务占槽阻止当前事实发布。自定义快照保留预算四 key 与默认四 key 分离。

现有 Analysis store 全局 `MAX_KEYS=16`、每 key 保留两份发布、单 payload 上限 32MiB。S2 必须测量当前 family 总 key 占用与新增四组合，证明正常维护不会驱逐仍需读取的 Analysis/Records/艺人发布。必要时为维护集合明确保留名额/按 family 轮转，并做容量回归；不直接增大 LRU 或无界保存全库 DataFrame。构建结束只释放本次重型 frame，不清空别的可用结果。

## 4. 前端消费与交互

在 `VersusExperience` 或共用 hook 中，过滤设置加载完成且至少两个对象有效时启动三条请求。`VersusScoreboardSection` 消费已准备结果，不承担以挂载时机控制请求的职责。

- 所有 GET/POST 读取继续使用 TanStack Query。基础与排名使用各自 queryKeys，完整含对象身份、相关过滤条件、统计合同版本；按实体集合规范化 key，队列上下移动只重排展示，不重新计算。
- 使用 Query 提供的 AbortSignal；移除对象、切类型、切过滤条件或离页后可取消失效请求，取消不等于 backend 已中止，后端结果仍须受上下文校验保护。
- “个人播放”栏目从对决开始即有固定行结构；基础和排名分别呈现加载、可用、不可用、真实 0，Phone/Compact/Desktop 共用事实与状态。
- 不以某一个对象先返回作为胜者。每行须全部当前对象拥有可比较数据后才计分，null/加载/错误不当作 0；部分数据只显示“已完成指标得分”，完整齐备后才给出最终总分与胜者。
- 一个请求失败时保留其他有效栏目，显示该组错误和手动重试。`snapshot_unavailable` 不自动反复重试；禁止以持续轮询制造后台负担。
- 不采用 placeholderData 展示另一种类型或过滤条件的旧结果。已有当前上下文结果可在同 key 重新获取时保留并显示更新状态。
- 专辑发行周期继续在原条件下请求，不因重排个人统计顺便扩大功能入口。

真实浏览器集成发现发行周期冷准备与个人请求竞争 CPU。实现增加两项有界收口：发行周期只复用 exact 周榜发布、共享紧凑全局计次基线并读取目标主艺人事件；不重算全库周排名或对周期不消费的时长事实。第三、第四对象变化使用共享 220ms 稳定窗口，两个对象仍立即开始；等待计入基础行可见门槛，重排同集合不触发请求。发行周期在当前个人请求结束后启动，其计次口径、主艺人/source album 范围与既有周期指标保持，周排名的完整结束周边缘规则单独核对。具体失败与对账见[验收报告](../reports/2026-10-08-versus-personal-statistics-performance-acceptance.md)。

### 9.1 已证明的成本与待验证假设
